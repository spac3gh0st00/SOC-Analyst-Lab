Both VMs need to ping each other before anything else. If not, check VMware — both should be on the same host-only or NAT adapter. Run ping [LINUX_IP] from Windows PowerShell to confirm.

setup
▼
Run Get-Service sysmon64 in PowerShell. Then check Event Viewer → Applications and Services Logs → Microsoft → Windows → Sysmon/Operational. You should see events populating.

setup
▼
Log into LimaCharlie, grab the sensor installer for your org, run it on Windows as Administrator. Confirm the sensor shows green/online in the LC dashboard before moving on.
Relaunch Sliver C2, generate a fresh implant and confirm session checks in
setup
▼
Always generate a new implant — don't reuse old ones. Run sliver-server → generate --http [LINUX_IP] → stage via Python HTTP → execute on Windows. Confirm session appears in Sliver console.
PHASE 1 Wire in Elastic SIEM ~4–6 hrs ▼
Provision a third Ubuntu 22.04 VM for Elastic Stack
siem
▼
Minimum 4GB RAM, 2 vCPUs, 50GB disk. Give it a static IP on the same network. This VM runs both Elasticsearch and Kibana. Don't go below the RAM minimum or Elasticsearch will crash.
Install Elasticsearch and save the generated superuser password
siem
▼
The install prints the elastic superuser password once. Copy it immediately. If you miss it: sudo /usr/share/elasticsearch/bin/elasticsearch-reset-password -u elastic
Install Kibana and bind to 0.0.0.0 so it's reachable from host browser
siem
▼
Most common gotcha: Kibana defaults to localhost. Edit /etc/kibana/kibana.yml and set server.host: "0.0.0.0". Full setup commands in docs/elastic-setup.md.
Install Winlogbeat on Windows VM, point at Elastic, enable Sysmon module
siem
▼
Edit winlogbeat.yml — set output.elasticsearch.hosts to your Elastic VM IP. Add ssl.verification_mode: none and Microsoft-Windows-Sysmon/Operational to the event_logs list.
Confirm Sysmon events flow into Kibana Discover
siem
▼
In Kibana → Discover, search event.module: sysmon. If nothing shows, check Winlogbeat logs on Windows: Get-Content "C:\ProgramData\winlogbeat\logs\winlogbeat" -Tail 50
PHASE 2 Expand attack coverage — 5 new TTPs ~2–3 hrs each ▼
Persistence via scheduled task
attackT1053.005
▼
Use schtasks.exe from your Sliver session to register a task that runs the implant on login. One of the most common real-world persistence mechanisms — high value for interviews.
Lateral movement with PsExec
attackT1021.002
▼
Use Sliver's psexec module or SysInternals PsExec. Watch for Event ID 7045 (service install) and 4624 (network logon) in Elastic — the canonical lateral movement signals analysts hunt for.
Defense evasion via process injection
attackT1055
▼
Inject a payload into a legitimate process like notepad.exe. Look for Sysmon Event ID 8 (CreateRemoteThread) in Elastic — anomalous cross-process memory writes are a strong detection signal.
Execution via PowerShell encoded command
attackT1059.001
▼
Run a base64-encoded payload using -EncodedCommand. Detect via KQL: process.command_line: *-enc*. Extremely common in real-world phishing payloads and living-off-the-land attacks.
Persistence via new local admin account
attackT1136.001
▼
Create a user and add to Administrators via net user / net localgroup. Detect via Event ID 4720 (account created) and 4732 (added to privileged group) in Windows Security logs.
PHASE 3 Write detections for each TTP parallel with Phase 2 ▼
Write a KQL hunt query in Elastic Discover for each attack
detect
▼
After every attack, open Kibana Discover and hunt for it manually. Write a KQL query that finds it reliably and save it. Do this immediately after each attack while the context is fresh.
Promote each KQL query to a detection rule with MITRE tags and alert
detect
▼
Kibana → Security → Detection Rules → Create Rule. Tag each with the correct MITRE tactic and technique. Re-run the attack and confirm the alert fires. Screenshot it for your incident report.
Mirror critical detections as D&R rules in LimaCharlie
detect
▼
Having logic in both platforms shows cross-tool fluency. Minimum: mirror the LSASS dump and scheduled task rules. Add an automated response action (process kill) to at least one.
