Boot Windows and Linux VMs, confirm static IPs and inter-VM connectivity
setup
▼
Both VMs need to ping each other before anything else. If not, check VMware — both should be on the same host-only or NAT adapter. Run ping [LINUX_IP] from Windows PowerShell to confirm.
Verify Sysmon is running and generating events
setup
▼
Run Get-Service sysmon64 in PowerShell. Then check Event Viewer → Applications and Services Logs → Microsoft → Windows → Sysmon/Operational. You should see events.
Re-enroll LimaCharlie sensor on Windows VM and confirm online
setup
▼
Log into LimaCharlie, grab the sensor installer for your org, run it on Windows as Administrator. Confirm the sensor shows green/online in the LC dashboard before moving on.
Relaunch Sliver C2, generate a fresh implant and confirm session checks in
setup
▼
Always generate a new implant — don't reuse old ones. Run sliver-server → generate --http [LINUX_IP] → stage via Python HTTP → execute on Windows. Confirm session appears in Sliver console.
PHASE 1 Wire in Elastic SIEM ~4–6 hrs ▼
Provision a third Ubuntu 22.04 VM for Elastic Stack
siem
▼
Minimum 4GB RAM, 2 vCPUs, 50GB disk. Give it a static IP on the same network. This VM runs both Elasticsearch and Kibana. Don't go below the RAM minimum or Elasticsearch will OOM.
Install Elasticsearch and save the generated superuser password
siem
▼
The install prints the elastic superuser password once. Copy it immediately. If you miss it, reset with sudo /usr/share/elasticsearch/bin/elasticsearch-reset-password -u elastic.
Install Kibana and bind to 0.0.0.0 so it's reachable from host browser
siem
▼
Most common gotcha: Kibana defaults to localhost. Edit /etc/kibana/kibana.yml and set server.host: "0.0.0.0". Then access it from your host at http://[ELASTIC_VM_IP]:5601.
Install Winlogbeat on Windows VM, point at Elastic, enable Sysmon module
siem
▼
Edit winlogbeat.yml — set output.elasticsearch.hosts to your Elastic VM IP and add ssl.verification_mode: none. Add Microsoft-Windows-Sysmon/Operational to the event_logs list.
Confirm Sysmon events flow into Kibana Discover
siem
▼
In Kibana → Discover, search event.module: sysmon. If nothing shows, check Winlogbeat logs on Windows: Get-Content "C:\ProgramData\winlogbeat\logs\winlogbeat" -Tail 50.
PHASE 2 Expand attack coverage — 5 new TTPs ~2–3 hrs each ▼
Persistence via scheduled task
attackT1053.005
▼
Use schtasks.exe from your Sliver session to register a task that runs the implant on login. SOC interviews love this — it's in the top 5 most common real-world persistence mechanisms.
Lateral movement with PsExec
attackT1021.002
▼
Use Sliver's psexec module or SysInternals PsExec. Watch for Event ID 7045 (service install) and 4624 (network logon) in Elastic — these are the canonical lateral movement signals analysts hunt for.
Defense evasion via process injection
attackT1055
▼
Inject a payload into a legitimate process like notepad.exe or explorer.exe. Look for Sysmon Event ID 8 (CreateRemoteThread) in Elastic — anomalous cross-process memory writes are a strong detection signal.
Execution via PowerShell encoded command
attackT1059.001
▼
Run a base64-encoded PowerShell payload using the -EncodedCommand flag. Detect via KQL: process.command_line: *-enc* or *-EncodedCommand*. Extremely common in real-world intrusions and phishing payloads.
Persistence via new local admin account
attackT1136.001
▼
Create a user and add to Administrators via net user / net localgroup. Detect via Event ID 4720 (account created) and 4732 (added to privileged group) in Windows Security logs.
PHASE 3 Write detections for each TTP parallel with Phase 2 ▼
Write a KQL hunt query in Elastic Discover for each attack
detect
▼
After every attack simulation, open Kibana Discover and hunt for it manually. Write a KQL query that finds it reliably. Save each as a saved search. This is your growing detection library.
Promote each KQL query to a detection rule with MITRE tags and alert
detect
▼
Kibana → Security → Detection Rules → Create Rule. Tag each rule with the correct MITRE tactic and technique. Re-run the attack afterward and confirm the alert fires. Screenshot it.
Mirror critical detections as D&R rules in LimaCharlie
detect
▼
Having logic in both platforms shows cross-tool fluency — something interviewers ask about. Minimum: mirror the LSASS dump and scheduled task rules. Add an automated response action to at least one.
